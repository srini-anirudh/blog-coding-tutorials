Part 01

Core attention: one function, one head

Goal Write attention with every intermediate tensor visible, and show it equals PyTorch’s version.

Attention takes three tensors. Queries ask. Keys answer how relevant they are. Values hold what gets passed along. Each output row is a weighted average of the value rows, and the weights come from query-key dot products.

Derivation inHow attention moves information @@LIST attnzoo/core.py | def scaled_dot_product_attention( | return out, weights | 21-27 | Listing 1The reference. The highlighted lines are the whole algorithm.

Read the shapes in the docstring first. The leading dimensions are free, so the same function serves one head or many. The rows of scores are queries and the columns are keys. That is why the softmax runs on the last axis: each query spreads its attention over the keys.

The scale matters. If q and k have unit-variance entries, their dot product has variance d. Dividing by sqrt(d) brings it back to 1, so the softmax does not saturate as the head grows.

Run it on the smallest case that shows everything: two queries, three keys, four dimensions.

Part 02

Masks: deciding who may read whom

Goal Build every mask you will meet by hand, look at each one, and catch the two classic mask bugs.

A mask is a boolean tensor of shape (Nq, Nk). True means this query may read this key. We use the same convention as PyTorch’s SDPA. The most important mask is causal, and it has one detail that many first versions get wrong.

@@LIST attnzoo/masks.py | def causal_mask( | return k_pos <= q_pos | 7-9 | Listing 4The causal mask, built from absolute positions. It lines up with the bottom-right corner, which is what decoding with a cache needs. We return to this in part 4.

Padding is different. It belongs to keys, not to pairs. No query should read a pad token, so the mask has shape (B, 1, 1, Nk) and broadcasts over heads and queries.

@@LIST attnzoo/masks.py | def padding_mask( | return attention_mask.bool()[:, None, None, :] | |

Multimodal sequences need one more rule. Image patches have no reading order, so patches of one image may see each other in both directions. Text stays causal, and text after the image sees all of it.

@@LIST attnzoo/masks.py | def multimodal_mask( | return (causal | same_image)[:, None] | 11-13 | Listing 5The multimodal mask is a causal mask plus one extra OR term.

Try them. Pick a type and move the sliders. The printed tensor is what the matching function in masks.py returns.

Two mask bugs come up again and again. The first inverts the mask with triu. The second blocks every key for a query, so the softmax has only minus infinity left to normalise.

@@OUT break_it.txt | 2. Mask inverted | the causality check | scripts/break_it.py @@OUT break_it.txt | 3. A row with no visible key | torch SDPA row 0 | scripts/break_it.py

A NaN that appears in one whole row is the signature of a fully blocked query. Left padding produces exactly this: a pad token at position 0 can only see itself, and it is masked. SDPA returns zeros for such a row, so our library backend matches it explicitly.

Part 03

Head sharing: MHA, MQA and GQA

Goal Write multi-head attention, fuse its projections, then share keys and values across heads until one module covers all three.

Heads are a reshape

Multi-head attention does not add a separate network per head. It projects to the full width and cuts the result into H slices, so D = H * dh. Two helpers do the cutting and the gluing.

@@LIST attnzoo/heads.py | def split_heads( | return x.transpose(1, 2).contiguous().view(b, n, h * d) | 7,17 | Listing 6Reshape, then move the head axis next to the batch axis so the matmuls batch over (B, H).

The contiguous() call is not decoration. After transpose, the elements are no longer in the order view needs, and view refuses to run. See the shape errors in the Break it box below.

@@LIST attnzoo/mha.py | class MultiHeadAttention | return self.o_proj(merge_heads(out)) # mix | 15-19 | Listing 7Multi-head attention. The output projection is what lets heads exchange information.

Fused projections

Three linear layers mean three matmuls. One wide layer does the same work in one call, and the output is split afterwards. The weight of the fused layer is the three weights stacked. So we can copy one into the other and check the outputs match.

@@LIST attnzoo/mha.py | class FusedQKVAttention | return self.o_proj(merge_heads(out)) | 10 | Listing 8One projection, then chunk. @@OUT shapes.txt | --- three Linear | max |separate | scripts/shapes.py

Fusing does not change the maths or the parameter count. On this CPU it saved a little, 14.2 ms against 16.7 ms per call. The real benefit of fusing is on accelerators, where one big matmul can use the hardware better than three small launches. GPT-2 style code (c_attn) and nn.MultiheadAttention both use it.

Sharing keys and values

Queries are used once and thrown away. Keys and values for past tokens stay in the cache for the whole decode. So the cache pays for KV width, while the queries do not. That asymmetry is the idea behind multi-query attention. Keep H query heads, but use a single shared key and value head.

@@LIST attnzoo/mha.py | class MultiQueryAttention | return self.o_proj(merge_heads(out)) | 8-9,14-15 | Listing 9MQA. The shared K and V have one head of width dh, and broadcasting does the rest.

GQA sits between the two. Groups of n_rep = Hq / Hkv query heads share one KV head. The maths is the same once the KV heads are repeated to line up with the query heads.

@@LIST attnzoo/heads.py | def repeat_kv( | return x[:, :, None, :, :] | 4-5,9 | Listing 10Query head h reads KV head h // n_rep.

Shape mistakes are the friendly kind of bug. They fail at once with a message.

Nuance

The parameter table shows GQA is not only about the cache. Going from MHA to GQA with Hkv = 8 also removes 37.5% of this layer’s weights. Whether that hurts quality is an empirical question. Ainslie et al. report that GQA with a moderate head count stays close to MHA while training faster than MQA. Our tests cover correctness, not quality, and this tutorial makes no quality claim of its own.

Part 04

RoPE and the KV cache

Goal Put positions inside attention, stop recomputing history, and check the memory formula against real tensors.

RoPE inside attention

RoPE encodes position by rotating queries and keys. The rotation has a useful property: the dot product of a rotated query and a rotated key depends only on how far apart they are. We build the tables once.

Derivation inHow models know where they are @@LIST attnzoo/rope.py | class RotaryEmbedding | return self.cos_cached[position_ids] | 10-13 | Listing 11The frequencies and the cos and sin tables. Each pair of dimensions rotates at its own speed. @@LIST attnzoo/rope.py | def rotate_half( | return rotate(q, cos, sin), rotate(k, cos, sin) | 9-10 | Listing 12The rotation. Values are never rotated. Their job is content, not matching.

This layout pairs dimension i with dimension i + d/2. It is the Llama and Hugging Face convention, and matching it lets us test against their code directly.

Two modes of attention

Generation runs in two modes with very different shapes. Prefill processes the prompt: Nq = Nk = N. Decode processes one new token: Nq = 1, and Nk = T, the whole history. Past keys and values never change, so we store them.

Break it

Two decode bugs produce wrong text without any error. First, is_causal=True looks like the obvious flag. But SDPA aligns it top-left, so the new token sees only key 0. Second, forget the offset and RoPE restarts at position 0 for every new token.

The KV memory formula

The cache holds one key tensor and one value tensor per layer. So its size is:

M_KV = 2 * L * B * S * Hkv * dh * b

Here L is layers, B is batch, S is sequence length, and b is bytes per number. Do not trust a formula you have not measured. The benchmark fills the cache through real forward passes and compares byte counts. On MPS it also reads the allocator.

@@TERM .venv/bin/python c03-attention/benchmarks/bench_kv_memory.py | bench_kv_memory.txt | Part 1 |

Formula and tensors agree exactly in every row. In the MPS column, the allocator growth is a little larger than the tensors, which is the overhead of the live input and layer buffers. The formula counts the cache, and the machine has to hold a bit more.

Part 2 of that output applies the verified formula to a full-size layer stack. A 128K-token context costs 64 GiB with MHA and 16 GiB with GQA at Hkv = 8, in bf16, before a single weight is loaded. That is why cache layout is an architecture decision. Try your own numbers.
