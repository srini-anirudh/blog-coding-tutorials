# Hardware: AMD EPYC 7R13, 8 threads, torch 2.15.0
# Command: python labs/what-autograd-actually-does/scripts/09_precision_and_order.py

1. One node receives 4096 gradient contributions. Sum them in 20 random orders:
dtype    distinct results  max - min  relative spread
-------  ----------------  ---------  ---------------
float32  18                4.10e-02   3.7e-06
float64  18                6.73e-11   6.1e-15
Same numbers, same machine, different order: different bits. Engines that schedule children on several
threads inherit this. Deterministic modes fix the order, and pay for it in throughput.

2. Loss scaling is exact for powers of two (float32 MLP, one backward):
  scale        1: gradients equal to unscaled bit for bit: True; max abs diff 0.0e+00
  scale    65536: gradients equal to unscaled bit for bit: True; max abs diff 0.0e+00
  scale     1000: gradients equal to unscaled bit for bit: False; max abs diff 3.0e-08

3. Gradients near 1e-8 in low precision (loss = 1e-4 * sum(w * x), x ~ 1e-4, so dL/dw ~ 1e-8):
dtype     loss scale  grads that are 0  relative error
--------  ----------  ----------------  --------------
float16   1           100.0%            1.0e+00
float16   4096        0.0%              4.4e-04
float16   65536       0.0%              inf
bfloat16  1           0.0%              2.7e-03
float16's smallest subnormal is about 6e-8, so these gradients all become 0. Scaling the loss by 2^12 lifts
them into range. 2^16 = 65536 is above float16's largest value (65504), so the scaled seed is already inf: this
is why loss scalers lower the scale when they see an inf. bfloat16 keeps the gradients without any scaling.
